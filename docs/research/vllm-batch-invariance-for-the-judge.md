# vLLM batch invariance for the pooled judge

Research note for [issue #65](https://github.com/kreuzhofer/chat3d-app/issues/65) (child of map #45). Reading only: no cluster access, no experiments. Written 2026-09-06 against primary sources at the versions named below. The decision is a human's; the last section stays factual.

## Question

What keeps the pooled local judge reproducible when it shares the pool with chat and codegen traffic — vLLM's `VLLM_BATCH_INVARIANT=1` on this recipe, a dedicated judge pool, or serializing the judge's calls — and what does each cost?

## What the facts are pinned to

- **The pool's vLLM.** `0.1.dev20051+g487ecf187` (observed on the glm deployment in [#53](https://github.com/kreuzhofer/chat3d-app/issues/53); the ticket takes it as the pool's version). That is upstream `main` commit [`487ecf187d3dfe74d2cf6119a92881dba403c219`](https://github.com/vllm-project/vllm/commit/487ecf187d3dfe74d2cf6119a92881dba403c219), committed **2026-08-25T13:16Z** ("align video processor with transformers"). Against the release tags it is 142 commits past the `v0.28.0` branch point (`compare/v0.28.0...487ecf187`: 142 ahead, 142 behind); no `v0.29.0` tag existed on 2026-09-06. Every "at the pool's commit" fact below was read from that tree, with file and line.
- **The judge.** `qwen3.8-27b-nvfp4`, an NVFP4 quantization of [`Qwen/Qwen3.8-27B`](https://huggingface.co/Qwen/Qwen3.8-27B). Its [`config.json`](https://huggingface.co/Qwen/Qwen3.8-27B/raw/main/config.json) declares `architectures: ["Qwen3_5ForConditionalGeneration"]`, `model_type: qwen3_5`, 64 text layers of which **48 are `linear_attention` (Gated DeltaNet) and 16 `full_attention`** (3:1 interleave), a 27-layer vision tower (patch 16, temporal patch 2), and an MTP head (`mtp_num_hidden_layers: 1`). vLLM maps that class to `vllm/model_executor/models/qwen3_5.py` (`vllm/model_executor/models/registry.py:595`).
- **The measurement this note does not re-derive.** From [#61's resolution](https://github.com/kreuzhofer/chat3d-app/issues/61): at temperature 0, thinking off, guided JSON, on the three-replica pool at chat3d concurrency 3, qwen reproduces itself byte-for-byte as the pool's sole tenant (arm 3 vs arm 1: 124/125 raw responses byte-identical, 511/511 items identical, 0 hard flips) and flips 3.3% of items (17 of 511, all at positions 82–115) once a chat + multi-agent codegen session lands on the same served name. During the clean arms the gateway poll showed peak in-flight 1 on every replica ([#59 follow-up](https://github.com/kreuzhofer/chat3d-app/issues/59)), i.e. each replica was running one judge request at a time.

## Facts

### 1. What `VLLM_BATCH_INVARIANT=1` does at the pool's commit

Source: the tree at `487ecf187`; the [feature doc](https://github.com/vllm-project/vllm/blob/487ecf187d3dfe74d2cf6119a92881dba403c219/docs/features/batch_invariance.md) and [PR #40193](https://github.com/vllm-project/vllm/pull/40193) (merged 2026-04-23) for the selector rules.

- **Definition.** `vllm/envs.py:616-618`: `VLLM_BATCH_INVARIANT` default `0`; comment "Enable batch-invariant mode: deterministic results regardless of batch composition. Requires NVIDIA GPU with compute capability >= 9.0." The feature doc says "compute capability 8.0 or higher" (Ampere support was added by [#38427](https://github.com/vllm-project/vllm/pull/38427), merged 2026-04-02). The doc calls the feature "currently in beta" and says "Enabling batch invariance may impact performance compared to the default non-deterministic mode" — no number.
- **Initialization** (`vllm/v1/worker/gpu_worker.py:1379-1381` → `vllm/model_executor/layers/batch_invariant.py:984-993`, `902-927`): sets NCCL/all-reduce environment (`VLLM_ALLREDUCE_USE_SYMM_MEM=0`, single-channel tree all-reduce, `VLLM_USE_AOT_COMPILE=0`); disables TF32 (`fp32_precision = "ieee"` for matmul, cuDNN conv and RNN); registers Triton overrides for `aten::bmm`, `_log_softmax`, `softmax`, `mean.dim` on all platforms; and branches on the GPU: on compute-capability family 8.x it also installs Triton persistent-matmul overrides for `mm/addmm/matmul/linear`; on every other CUDA device it instead relies on cuBLAS with `CUBLAS_WORKSPACE_CONFIG=":16:8"` and `CUBLASLT_WORKSPACE_SIZE=1`, with the comment "Hopper (SM90) and Blackwell (SM100): the only source of batch variance is split-k, which we disable via the cuBLAS workspace config." Nothing in the file names the 12.x family.
- **Layers.** RMSNorm uses `rms_norm_batch_invariant` (`layernorm.py:101-108`); unquantized linear and embedding use `linear_batch_invariant` (`linear.py:210-211`, `vocab_parallel_embedding.py:73-74`); fused MoE drops tuned configs and forces `SPLIT_K: 1` (`fused_moe/fused_moe.py:1121-1123`, `1302-1309`); modular MoE kernels are rejected unless they declare `_supports_batch_invariance()` (`fused_moe/modular_kernel.py:587-588`, default `False` at `674-680`). Tensor-parallel only: custom all-reduce off (`config/parallel.py:1003`), NCCL symmetric memory off (`cuda_communicator.py:249`). The `fuse_allreduce_rms` disable ([#51292](https://github.com/vllm-project/vllm/pull/51292), fixing [#51290](https://github.com/vllm-project/vllm/issues/51290) "not deterministic under TP>1") merged 2026-08-25T19:16Z — six hours **after** the pool's commit, so it is not in this build; it only matters for TP>1, and the pool's replicas are TP=1.
- **Attention backends.** The selector passes `use_batch_invariant=envs.VLLM_BATCH_INVARIANT` (`vllm/v1/attention/selector.py:167`); `AttentionBackend.supports_batch_invariance()` defaults to `False` (`vllm/v1/attention/backend.py:276-277`) and a non-supporting backend is invalid under the flag (`backend.py:389-390`). At this commit the backends declaring support are **FLASH_ATTN, TRITON_ATTN, FLEX_ATTENTION, FLASH_ATTN_MLA, TRITON_MLA** (`grep "def supports_batch_invariance" vllm/v1/attention/backends/`). **FLASHINFER does not declare it**, so auto-selection skips it and an explicit `--attention-backend FLASHINFER` raises `ValueError: Selected backend ... is not valid for this configuration` (`vllm/platforms/cuda.py:466-470`), even though the FlashInfer file still carries batch-invariant branches (fixed split sizes 2048/4096, `disable_split_kv`, a 2 GiB workspace: `flashinfer.py:700-706`, `1012-1013`). Non-MLA priority on a 12.x device is FLASH_ATTN → FLASHINFER → TRITON_ATTN → FLEX_ATTENTION → TURBOQUANT (`cuda.py:193-199`; only capability major 10 puts FlashInfer first).
- **What the flag changes inside FLASH_ATTN.** FA4 is refused ("FA4 currently uses batch-shape-dependent scheduling heuristics on SM100+, which breaks batch invariance", falls back to FA2: `fa_utils.py:163-170`, from [#36059](https://github.com/vllm-project/vllm/pull/36059), merged 2026-03-05 after 6/128 prompts violated invariance on a B200); the AOT schedule is off and `num_splits=1` (`flash_attn.py:557-560`, `590-591`, `1455`, `1764`, `1789`); cascade attention is disabled (`config/vllm.py:1658-1666`); TRT-LLM attention is disabled (`utils/flashinfer.py:411-413`); prefix caching is disabled for FLASHINFER/TRITON_MLA only (`layers/attention/attention.py:363-378`).
- **Reproducibility doc** ([`docs/usage/reproducibility.md`](https://github.com/vllm-project/vllm/blob/487ecf187d3dfe74d2cf6119a92881dba403c219/docs/usage/reproducibility.md)): "vLLM does not guarantee the reproducibility of the results by default"; "In online mode, you can only enable batch invariance"; and "Even with the above settings, vLLM only provides reproducibility when it runs on the same hardware and the same vLLM version."
- **Tested-model list at this commit:** DeepSeek V3/R1, Qwen3 dense (incl. AWQ), Qwen3 MoE (incl. `Qwen/Qwen3-Next-80B-A3B-Instruct`, an FP8 variant), Qwen2.5, Llama 3.x, gpt-oss, Mistral 7B, Phi-3.5. No vision-language model. The current `latest` docs add Qwen3-VL 2B/4B ("single image and video") after [#53531](https://github.com/vllm-project/vllm/pull/53531), merged **2026-08-30**, five days after the pool's commit.

### 2. The judge's Gated-DeltaNet layers: the flag refuses to start this model

- `vllm/v1/attention/selector.py:240-244` at the pool's commit:

  ```python
  if envs.VLLM_BATCH_INVARIANT and not mamba_attn_backend.supports_batch_invariance():
      raise RuntimeError(
          "VLLM batch_invariant mode is not supported for "
          f"{mamba_attn_backend.get_name()}."
      )
  ```

  The Qwen3.5-class GDN layer routes to `MambaAttentionBackendEnum.GDN_ATTN` (`vllm/model_executor/layers/mamba/gdn/base.py:50-51`); `GDNAttentionBackend` (`vllm/v1/attention/backends/gdn_attn.py`) contains no `supports_batch_invariance` override, so it inherits `False`. The enum at this commit is `MAMBA1, MAMBA2, SHORT_CONV, LINEAR, GDN_ATTN` (`registry.py:189-193`) — there is no Qwen-specific batch-invariant GDN backend. The check was added by [#40193](https://github.com/vllm-project/vllm/pull/40193) ("Adds batch-invariance check to the Mamba backend selector path"), merged 2026-04-23.
- **Upstream confirmation on this exact model.** [vllm#42960](https://github.com/vllm-project/vllm/issues/42960) (open, filed 2026-05-18 on v0.21.0 and nightly, A100): `RuntimeError: VLLM batch_invariant mode is not supported for GDN_ATTN.` — "a hard incompatibility — no fallback, no partial mode." Comment of **2026-09-01** (WenyueD): `Qwen/Qwen3.8-27B` (revision `1d4bf0f2…`) on **vLLM 0.28.0**, A800, bf16, TP=1: "even target-only initialization aborts with `RuntimeError: VLLM batch_invariant mode is not supported for GDN_ATTN`". Also [vllm#48613](https://github.com/vllm-project/vllm/issues/48613) (open, 2026-07-14, v0.25.1, Qwen3.5/3.6).
- **The two open fixes, neither merged on 2026-09-06.**
  - [PR #45819](https://github.com/vllm-project/vllm/pull/45819) (open since 2026-06-16, last push 2026-09-04, `mergeable_state: blocked`): declares support on `GDNAttentionBackend` and dispatches **each sequence separately** through the FLA kernels under the flag ("The FLA/Triton kernel's chunking depends on batch geometry; per-sequence dispatch guarantees bit-identical outputs regardless of batch size"). Validated on H100 NVL (SM90) with Qwen3.5-0.8B and Qwen3.6-35B-A3B; a third party reports Qwen3.5-35B-A3B-FP8 bit-identical at TP=1 and TP=4 on vLLM 0.29 with the patch. The automated review flags a CUDA-graph padding risk still to be fixed. No test on any 12.x device.
  - [PR #49827](https://github.com/vllm-project/vllm/pull/49827) (open since 2026-07-25): a Qwen-specific backend "on CUDA SM90+". Its description documents three ways traffic shape changed GDN arithmetic on H100: a cached decode row switched recurrent kernels when a prefill arrived in the same step; FlashInfer GDN prefill with `use_cp="auto"` changed 4,284 of 131,072 outputs between batch sizes 1 and 8; and scheduler chunk boundaries (`[73, 128, 192]` vs `[64, 128, 192]`) changed 54,452 output elements. These are the mechanisms behind #61's co-tenant flips, stated by the author for the GDN layers specifically.
- The doc's tested list naming `Qwen3-Next-80B-A3B` (a GDN model) predates the selector check; a comment on #45819 (2026-09-03) says `Qwen3-Next-80B-A3B-Instruct-FP8` is blocked on that PR.

### 4. Speculative decoding and MTP

- At the pool's commit there is **no batch-invariance code in the speculative-decoding path**: `grep -rin batch_invarian vllm/v1/spec_decode/ vllm/config/speculative.py vllm/v1/sample/` is empty. The flag neither disables spec decode nor changes the drafter or the rejection sampler.
- [PR #52522](https://github.com/vllm-project/vllm/pull/52522) (open, 2026-08-16, updated 2026-09-03) "extends batch invariance to stochastic speculative decoding" (preemption recovery; validated with EAGLE3, DFlash, DSpark). Its author: "I didn't find a proper model with MTP to test, because GDN hasn't been supported with batch-invariance now." So the flag × MTP × this model family is untested upstream.
- The 2026-09-01 comment on #42960 (same model, no batch invariance, temperature 0) reports target-only and DFlash2 decoding diverging at token 44 on an **exact logprob tie** (`3710 = 9930 = -0.9475287199`), resolved differently by execution path — "execution-path-dependent argmax tie-breaking". Ties are a flip source independent of batching.
- On record in this map (#59 resolution): glm-5.3-flash with MTP on (`num_spec_tokens=4`, #53) gave 5 distinct replies and 2 boolean flips in 32 identical sequential requests on an idle deployment; MTP is dgx-manager's leading candidate there; disabling it needs a recipe variant and redeploys (`num_speculative_tokens=0` does not switch it off). Whether the qwen pool's recipe runs MTP is not in the repo — see Open questions.

### 5. NVFP4 weights under the flag, on a 12.x device

- Kernel selection (`vllm/model_executor/kernels/linear/__init__.py:986-1019`): with the flag, NVFP4 linear layers are **forced to the CUTLASS batch-invariant kernel when `cutlass_fp4_supported()`, otherwise to the emulation kernel** ("VLLM_BATCH_INVARIANT is set but the batch-invariant NVFP4 kernel is not supported on this platform; falling back to emulation"). It "overrides `--linear-backend`" — Marlin (weight-only) and FlashInfer paths are not used under the flag regardless of recipe.
- The gate is "was the kernel compiled for this SM": `cutlass_scaled_mm_supports_fp4` (`csrc/libtorch_stable/quantization/fp4/nvfp4_scaled_mm_entry.cu:71-83`) requires CUDA runtime ≥ 12.8 and returns true for 100–119 only under `ENABLE_NVFP4_SM100`, for 120–129 only under `ENABLE_NVFP4_SM120`. Upstream's CMake lists `12.1` with CUDA ≥ 13 (`CMakeLists.txt:129`) and the family/arch targets `12.1f` / `12.1a` (`:464`, `:467`). Whether the sparkrun image was built with those targets is an image fact (#53 describes it as a day-0 arm64 build "with an sm_121 overlay").
- The SM120 CUTLASS kernel has an explicit batch-invariant branch: a persistent tile scheduler with `static_assert(... "batch_invariant requires a persistent tile scheduler; stream-K or split-K would break numerical invariance")` (`nvfp4_scaled_mm_sm120_kernels.cu:212-221`). History: [#39322](https://github.com/vllm-project/vllm/pull/39322) (merged 2026-04-08), [#39912](https://github.com/vllm-project/vllm/pull/39912) (CUTLASS linear, merged 2026-05-23), [#40372](https://github.com/vllm-project/vllm/pull/40372) (CUTLASS MoE, merged 2026-08-05; irrelevant to a dense 27B). The batch-invariance test for NVFP4 (`tests/v1/determinism/test_nvfp4_batch_invariant.py`) runs `nm-testing/TinyLlama-1.1B-Chat-v1.0-NVFP4` on any CUDA device — no 12.x result is published.
- FlashInfer's FP4 kernels: CuTe-DSL "requires sm_10x" (`nvfp4/flashinfer.py:38-39`); the b12x GEMM needs "SM120+" (`:315-321`) — neither is used under the flag. Related platform gap: [vllm#43906](https://github.com/vllm-project/vllm/issues/43906) (open, 2026-05-28) shows the pattern of `is_device_capability_family(100)` gates excluding SM_121 (MXFP8 MoE falls back to Marlin on DGX Spark).

### 6. Does the GB10 meet the mode's stated requirements?

- NVIDIA lists **"12.1 — NVIDIA GB10 (DGX Spark)"** on the [CUDA GPUs compute-capability table](https://developer.nvidia.com/cuda-gpus) (B200/GB200 10.0, B300 10.3, RTX PRO 6000 / RTX 50 series 12.0). The [DGX Spark product page](https://www.nvidia.com/en-us/products/workstations/dgx-spark/): GB10, Blackwell, 20-core Arm, 128 GB LPDDR5x at 273 GB/s, "Up to 1 PFLOP FP4" (sparse), 5th-generation Tensor Cores.
- **Stated thresholds are met on paper:** vLLM's GPU requirement is compute capability ≥ 7.5 (`docs/getting_started/installation/gpu.cuda.inc.md:9`), the feature doc says ≥ 8.0, the env comment ≥ 9.0. `is_device_capability_family(120)` is true for 12.1 (major-only comparison, `vllm/platforms/interface.py:481-493`).
- **But no code path, test or report names the 12.x family for this feature.** `batch_invariant.py` takes the cuBLAS-workspace branch on 12.1 with a comment that names SM90 and SM100 only; the determinism tests have no capability-12 case; a search of the vLLM tracker for batch invariance with "GB10", "DGX Spark", "sm121" or "12.1" returns nothing. The only 12.x-family data point is the negative Qwen3-VL report on an RTX 5090 (§3).
- **Upstream SM121 support is itself an open PR.** [#31740](https://github.com/vllm-project/vllm/pull/31740) "Add SM121/GB10 (DGX Spark) Blackwell-class GPU support" (open since 2026-01-05; adds `is_blackwell_class`, auto-sets `TRITON_PTXAS_PATH`, notes FlashInfer-MLA/CUTLASS-MLA are SM100-only). The pool runs a custom image, so upstream gaps may be patched there.
- **Blackwell + torch.compile history.** [vllm#32992](https://github.com/vllm-project/vllm/issues/32992) (B200: invariance held in eager, broke under torch.compile, Jan 2026) was closed "completed" 2026-03-05, the day the FA4→FA2 fallback merged; the proposed "force eager on Blackwell" fix [#33383](https://github.com/vllm-project/vllm/pull/33383) was rejected. [vllm#39096](https://github.com/vllm-project/vllm/issues/39096) (torch.compile / CUDA graphs break invariance on SM<90) is still open. The flag does not force eager mode anywhere at the pool's commit.
- **Platform caveats from the kernel libraries the mode leans on.** Triton (the batch-invariant `bmm`/`softmax`/`mean`/RMSNorm kernels and TRITON_ATTN): [triton#10331](https://github.com/triton-lang/triton/issues/10331) (open) — on sm_121 any Triton-lowered path fails with "no kernel image is available" unless `TRITON_PTXAS_PATH` points at a CUDA ≥ 13 `ptxas`; `TRITON_OVERRIDE_ARCH=sm90` is the wrong workaround. FlashInfer: the [DGX Spark support audit #3170](https://github.com/flashinfer-ai/flashinfer/issues/3170) (open, updated 2026-09-02) — `sm_120f` family wheels cover dense NVFP4 MMA on 121; [#4781](https://github.com/flashinfer-ai/flashinfer/issues/4781) (2026-08-27) — `flashinfer-cubin` wheels stop at 0.6.13 while vLLM ≥ 0.27 pins newer `flashinfer-python`, crash-looping stock installs on DGX Spark (the sparkrun image pins FlashInfer `0.6.18.dev20260819`, #53); [#3634](https://github.com/flashinfer-ai/flashinfer/issues/3634) — JIT-compiling SM120/121a CUTLASS FP4 kernels can OOM on unified-memory systems.

### 8. Operational alternatives: what the sources say about tenancy

- **Why tenancy matters.** Thinking Machines: nondeterminism comes from kernels lacking batch invariance while "the load (and thus batch-size) nondeterministically varies"; "From the perspective of an individual user, the other concurrent users are not an 'input' to the system but rather a nondeterministic property of the system." vLLM's feature doc defines the mode as output "independent of the batch size or the order of requests in a batch"; its reproducibility doc says online reproducibility exists only through the mode (§1). Neither vLLM's docs nor its scheduler offer per-client isolation of batch composition: continuous batching "batches all pending decode requests before scheduling any prefill operations" and chunked prefill mixes prefill chunks with decodes ([optimization doc](https://github.com/vllm-project/vllm/blob/487ecf187d3dfe74d2cf6119a92881dba403c219/docs/configuration/optimization.md)); `max_num_seqs` is "Maximum number of sequences to be processed in a single iteration" (`vllm/config/scheduler.py:63-64`). PR #49827's three mechanisms (§2) are the concrete ways a foreign request alters this model's arithmetic.
- **Serialization is the measured configuration.** #61's clean arms ran with one judge request in flight per replica (peak in-flight 1, #59 poll) and reproduced 124/125 responses byte-for-byte; the same request stream reproduced batch composition closely but not perfectly (one response differed with 0 item flips). A replica whose scheduler only ever sees one request (`--max-num-seqs 1`) has a fixed batch shape by construction, which is the property the mode exists to restore (Thinking Machines' argument) — but that is inference from the documents, not a measurement, and it serializes every tenant of that replica, not only the judge.
- **Reserving a served name.** On record from dgx-manager via #59: the gateway pools every deployment whose `publishedName` matches and routes least-outstanding with a per-name rotation (`gateway/selection.ts`); a display-name alias cannot have replicas because the name is substituted into each node's `served_model_name` and must be unique per active deployment. A judge-only pool is therefore its own deployment(s) under a distinct published name, and chat3d points only `vlm_eval` at it (a model row per served name; the provider row carries the gateway `baseURL`: `packages/backend/src/services/llm-config.service.ts:434`; purpose map). What a name reservation cannot do is keep other gateway clients off it — the session notes record the gateway as unauthenticated and the old alias shared with another team's smoke test (to confirm with dgx-manager). Cost of a replica: #59 measured 3 replicas at concurrency 3 as 2.7× one replica (13.0 vs 35.2 min per 125; 4.2–4.6 h per corpus pass, #61); a two-replica judge pool is unmeasured — linear extrapolation from #59's per-replica share gives ≈ 19.5 min per 125 and ≈ 6.8 h per corpus pass, and the chat/codegen pool would keep two replicas.
- **chat3d's own knobs.** A per-provider semaphore caps chat3d's in-flight calls to a provider (`packages/backend/src/utils/resource-limits.ts:44-65`; default `LLM_MAX_CONCURRENT=5`, `packages/backend/src/config.ts:141`; per-provider `max_concurrent` on the provider row, `llm-config.service.ts:45,108`; used by the judge at `visual-eval.service.ts:186` and `visual-eval-zoom.service.ts:251`), and `global.vlm_experiment_concurrency` (default 1, max 8) paces experiment runs (`generation-settings.service.ts:75`). Both limit chat3d's side only; they cannot exclude other tenants from a replica.
- **The production batch is already sequential.** `POST …/re-rate-stale/batch` (`workbench-instrument.service.ts:98-152`) hands its rows to `runBatchReEvaluate`, which is a plain `for (const example of examples) { … await reEvaluateExample(example.id) }` loop (`packages/backend/src/services/workbench-batch.service.ts`). One example is judged at a time, so from chat3d's side at most one judge call is in flight and the gateway lands it on one replica; the 4.2–4.6 h per corpus pass in #61 is the experiment-run figure at concurrency 3, while the batch's own pace is the sequential one (#59's smoke: 14–17 s per row, "one judge does the corpus in ~11 hours"). What the batch shares a replica with is therefore never its own traffic — only chat, codegen and other gateway clients.

## What this means for #65

Stated factually; the choice is a human's.

- **Option 1 (`VLLM_BATCH_INVARIANT=1`) is not runnable on the pool's vLLM for this model.** The engine refuses to start any GDN model under the flag (`selector.py:240-244`), reproduced with `Qwen/Qwen3.8-27B` on vLLM 0.28.0 on 2026-09-01. The earliest path is a custom build with an unmerged PR (#45819 or #49827), validated on H100 only, with the vision tower unverified on any 12.x device (the one 12.x report is negative), MTP untested, FlashInfer attention excluded, NVFP4 forced to CUTLASS-or-emulation, and no GB10 cost figure — the literature's cost is 1.6–2.1× on H100-class hardware.
- **Option 3 (serialize) is the known-good configuration.** #61's clean arms were, per replica, one judge request at a time; the reproducibility they showed is the property the flag would buy. What it costs is that chat and codegen traffic on those replicas waits (or goes elsewhere) during a re-rating pass; what it does not need is any vLLM change. Enforcing it at the replica (`--max-num-seqs 1`) rather than at the client is the version that also holds against foreign tenants, by the documents' argument, at the price of serializing everyone on that replica.
- **Option 2 (a judge-only pool) is a deployment change, not a vLLM change.** It needs a distinct published name (an alias cannot pool), and it holds only as long as nothing else uses that name — which the gateway does not enforce. The pool loses one replica of three for the chat purposes; the judge's corpus pass on two replicas is unmeasured (≈ 6.8 h by extrapolation).
- **Whatever is chosen, the fourth qwen arm the ticket asks for** (against arm 1, while a chat session runs) is the only evidence that will count on this hardware; nothing above substitutes for it.

## Facts from the cluster (2026-09-06, dgx-manager)

Added after the reading above, from the pool's own startup logs and the gateway source, relayed by dgx-manager. Facts only; the decision is on [#65](https://github.com/kreuzhofer/chat3d-app/issues/65).

- **Correction to "What the facts are pinned to."** The qwen pool does not run `0.1.dev20051+g487ecf187` — that string was read from the glm deployment in #53. All three nvfp4 replicas run image `ghcr.io/spark-arena/dgx-vllm-eugr-nightly:2026081501` (source `docker.io/eugr/spark-vllm`), engine **`v0.27.2rc1.dev113+g5cecfc013.d20260815`** (vLLM commit `5cecfc01375052698823fc401e31518fb32a981e`, FlashInfer `8044d94bf9acc5369857baf88d28906bb32bf264`), ten days older than the tree read above. The selector check that refuses GDN models under the flag ([#40193](https://github.com/vllm-project/vllm/pull/40193), merged 2026-04-23) predates both builds, so §2's conclusion stands; the file and line references in §1 and §5 are for `487ecf187` and may differ in the pool's tree.
- **Open question 1, answered.** Attention backend at startup: `FLASHINFER` ("out of potential backends: ['FLASHINFER', 'TRITON_ATTN']") for the text model, `FLASH_ATTN` for the vision tower. `kv_cache_dtype auto` (open question 4 does not arise). Quantization `compressed-tensors`. **MTP on: `speculative_config {'method': 'mtp', 'num_speculative_tokens': 5}`.** CUDA graphs enabled (`enforce_eager False`). `max_num_seqs 8`, `max_num_batched_tokens 2048`, prefix caching on, chunked prefill on, `max_model_len 262144`, `gpu_memory_utilization 0.88`, reasoning parser `qwen3`, reasoning effort pinned `medium` server-side (chat3d sends thinking off per request). `TORCH_CUDA_ARCH_LIST=12.1a`; the NVFP4 SM120 compile flag is not visible in the image metadata — undetermined, not absent.
- **`--max-num-seqs 1`** is not among sparkrun's restart overrides (port, gpuMem, maxModelLen, tensorParallel, artifactVariant). It needs a recipe variant with `max_num_seqs: 1` in its defaults (`./recipes` is bind-mounted; `POST /api/recipes/refresh` reloads the catalog), then a redeploy of the replica: ~20–30 minutes at today's load times for this model. No new image.
- **Gateway routing, confirmed.** Least-outstanding requests, ties broken by a rotation counter kept per published name (`gateway/selection.ts`, `gateway/rotation.ts`); candidates are every deployment whose `publishedName` matches exactly, ordered by id, filtered for health and agent-online. The counter is an in-process Map incremented synchronously at selection, so three requests reaching the selector one after another on an otherwise idle pool land on three distinct replicas; a co-tenant request between them shifts the counts, and two can share a replica while a third idles. Per-member live `inflight` is at `GET http://192.168.44.14:4000/api/gateway` (the #59 poll's endpoint).
- **No reservation is possible.** `proxy.ts` drops the `authorization` header deliberately; the gateway authenticates no one, so there is no per-client identity and no way to reserve a published name. Isolation is a separate served name: a recipe variant with its own `served_model_name` (poolable) — a deployment `displayName` also works but is unique per active deployment and can never pool. Who is on `qwen3.8-27b-nvfp4`: chat3d's own ten purposes and nothing else known; the other session's smoke test used the retired alias `qwen38-nvfp4-spark` and now uses `qwen3.8-27b-bf16`.
- **`qwen3.8-27b-bf16` on dgx-spark-01** is a SWE-bench Verified 500 rerun (~8 h remaining at 17:30 UTC, 8 concurrent, 0 waiting) under a no-restart, no-agent-roll freeze; not a place to send chat traffic today. Order of magnitude only, different workloads: bf16 43.9 tok/s at 8 concurrent on text prompts; one nvfp4 replica 15.3 tok/s steady on 8-image judge calls with guided JSON.
- **dgx-manager's caveat on MTP.** On glm, sole tenancy was not sufficient — 32 identical sequential requests on an idle server gave 5 distinct replies and 2 flipped booleans. On qwen, #61 measured 511/511 items and 124/125 byte-identical responses under the same MTP setting. A judge-only served name buys isolation from other traffic and nothing else; if MTP ever shows in a qwen pair, it needs its own recipe variant.
